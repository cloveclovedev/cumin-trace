# 要求と要件

cumin-trace の要求と要件をまとめた文書の入口。

## 全体

- [要求仕様書](overview.md): 解決したい課題、目的、位置づけ、プロダクトの構成、決めたこと、フェーズ
- [技術要素](technology.md): 使う技術と、選んだ理由
- [用語集](glossary.md): 語の意味と、使わない言い方
- [バックログ](backlog.md): v0.1 には入れないが、あとで取り入れたいこと

## カテゴリごとの要件

IDの接頭辞は `CTR` である。カテゴリごとにディレクトリを分け、要件のページ (`index.md`) と図を置いている。

| カテゴリ | ページ | 内容 |
|---|---|---|
| `FMT` | [要件文書の書式](format/index.md) | IDの形式、要件の書き方、フィールド、廃止の扱い |
| `TPL` | [テンプレートと skill](templates/index.md) | 要件文書のテンプレート、Agent と書くための skill、図の描画 |
| `CHK` | [書式検査](check/index.md) | 書式に沿っているかの確認 |
| `EXP` | [構造化データの出力](export/index.md) | 要件を JSON で出力する |
| `TRC` | [GitHub との対応づけ](trace/index.md) | 要件と要求Issue、実装Issueの結び付きと、進捗の決め方 |
| `SITE` | [サイト](site/index.md) | 要件文書をサイトとして表示する |
| `DASH` | [ダッシュボード](dashboard/index.md) | 要件の全体像と進捗を1ページで見る |
| `CMD` | [コマンド](command/index.md) | コマンドの一覧と、すべてのコマンドに共通する約束 |

## 受け入れのシナリオ

カテゴリをまたいで、v0.1 が目標を満たしたことを確かめるシナリオである。

| # | 場面 | 期待する結果 |
|---|---|---|
| 1 | 新しいリポジトリにテンプレートを生成し、書式検査を実行する | エラーなしで通る |
| 2 | 同じIDを2つのページに書く | 書式検査が、2つの場所を示して失敗する |
| 3 | 子を持たない要件が5つある。そのうち2つに対応する要求Issueが開いていて、別の1つに対応する要求Issueが completed で閉じている | 進行中が2つ、完了が1つ、未起票が2つになる |
| 4 | 3の状態でサイトをビルドする | ダッシュボードの要件の一覧に、進行中が2つ、完了が1つ、未起票が2つと出る |
| 5 | GitHub の token を設定せずにサイトをビルドする | 文書は表示される。ダッシュボードには、GitHub を読めなかったことだけが表示される |
