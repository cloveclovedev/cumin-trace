# バックログ

v0.1 には入れないと決めたが、あとで要件に取り入れたいことを書き留める。使い方は cumin-works のバックログと同じである。着手すると決めた項目は、要件のページに書いて、ここから消す。

項目ごとに、内容、後回しにした理由、見直すきっかけを書く。

## v0.2 の候補

### 要件の変更後の起票漏れの検出

v0.2 で最初に着手する。起票の漏れに気付けることは、cumin-trace の最も大事な目標の1つである。

要件の本文を直したのに、その変更のための要求Issueがないものを検出する。要件の本文が最後に変わった日時 (git の履歴) と、対応する要求Issueが閉じた日時を比べる。対応する要求Issueがすべて閉じたあとに本文が変わっていて、開いた要求Issueがなければ、「変更後に未起票」としてダッシュボードに表示する。要求Issueに SHA などを書く約束は要らない。

着手するときに、次の2つを決める。

- 誤字の修正のように、実装に影響しない変更の扱い。そのままでは、新しい要求Issueを書くまで表示が消えない
- 要求Issueが開いている間に本文が変わったときの扱い。その要求Issueが変更を反映しているかは、日時だけでは分からない

- 後回しにした理由: 作り始めの時期は、要件の変更よりも、新しい要件の起票が中心になる。それまでは [書式](format/index.md) の「要件を変えるとき」の運用で補う
- 見直すきっかけ: v0.1 が完了したとき

---

### 既存の文書にIDを付ける

cumin-works の `issue-states.md` の遷移や「上位要件のテスト」のように、すでにある文書の要件にIDを付ける。短いルールが多く並ぶ文書のために、表の形で要件を書けるようにするかを、このときに決める。遷移の名前 (「request the split」など) をIDの別名として扱うかも決める。

- 後回しにした理由: v0.1 では、新しく書くプロダクトの要件で書式を確かめる
- 見直すきっかけ: 新しいプロダクトの要件を、1つのカテゴリぶん書き終えたとき

---

### テストとの対応づけ (verify)

テストの名前やコメントに書いたIDを読み、検証が `test` の要件に、対応するテストがあるかを示す。

- 後回しにした理由: v0.1 では、要件から要求Issueまでの区間を先につなぐ
- 見直すきっかけ: 完了した要件の中に、テストのないものが見つかったとき

---

### 要求Issueを書くための skill

Agent が Maintainer と要求Issueを書くための skill を提供する。要件を書くための skill (CTR-TPL-005) の続きにあたる。cumin-trace は事実を答え、判断は Agent と Maintainer が行う。

skill は Agent に次の手順を指示する。

1. cumin-trace に、未起票の要件の一覧を尋ねる。これを出発点にする
2. 要件を、要求Issueの単位にまとめる。cumin-works を使うリポジトリでは、要求Issueの分割基準 (`requirement-sizing.md`) の基準と1つずつ突き合わせ、結果を Maintainer に示す
3. cumin-works の `requirement-issue.md` の形で下書きを書く。Requirements の各行の先頭にIDを書き、要件の本文を英語にする
4. Maintainer の確認のあとで起票する。`cumin/status/ready` は付けない
5. 起票のあとで cumin-trace に尋ね、未起票の要件が残っていないことと、存在しないIDを書いていないことを確かめる

v0.1 の要求Issue (#2 〜 #6) は、この手順を手で行って書いた。そのとき、2の突き合わせを省いたために、大きすぎる要求Issueを1つ書いた。5は、手元のコマンドでIDを比べて確かめた。

- 後回しにした理由: 1と5には、GitHub との対応づけ (CTR-TRC) が要る。v0.1 でそれができてから作る
- 見直すきっかけ: v0.1 が完了したとき。または、v0.2 の要求Issueを書き始めるとき

### 用語の検査

用語集の「使わない言い方」にある言い方が文書に出てきたら、報告する (例: レフェリーと審判)。

- 後回しにした理由: v0.1 では、skill が Agent に用語集を読ませることで補う
- 見直すきっかけ: Agent と書いた文書で、表記のゆれを直す手間が目立ってきたとき

---

### IDの使い回しの検出

git の履歴にあるIDが、別のタイトルで使われていたら報告する。

- 後回しにした理由: レビューで防げる
- 見直すきっかけ: 使い回しが実際に起きたとき

---

### バックログと未決事項の取り込み

バックログの項目と、各ページの「未決事項」を cumin-trace が読み、ダッシュボードに「決めること」として表示する。

- 後回しにした理由: 書式を増やす前に、要件だけで使ってみる
- 見直すきっかけ: 決めることの一覧を、ページをまたいで見たくなったとき

---

### 先のバージョンの要件を前もって書く

要件に「まだ起票しない」ことを表すフィールドを足し、未起票の一覧から外す。

- 後回しにした理由: 今は、作ると決めたことだけを要件文書に書き、後回しはバックログに書く
- 見直すきっかけ: 先のバージョンの要件を詳しく書きためるようになり、未起票の一覧が見にくくなったとき

---

### cumin-works のラベルによる細かい表示

進行中の要件のうち、Maintainer の対応を待っているものを分けて表示する。起票したがまだ `cumin/status/ready` を付けていないものと、受け入れを待っているものである。`cumin/status/*` のラベルを読んで見分ける。

- 後回しにした理由: v0.1 では、進捗を、要求Issueが開いているかと閉じた理由だけで決まる3つに絞る
- 見直すきっかけ: 進行中の要件が増えて、自分の対応を待っているものを見分けにくくなったとき

---

### 設計文書の要件IDの検査

設計文書の「要件」に書いたIDが、存在し、廃止されていないことを、書式検査で確かめる。設計文書のディレクトリは、設定のキー `designs_dir` (既定は `docs/ja/designs`) で指定する。今のエラーのうち、存在しないIDの参照と、廃止した要件の参照の2つを、そのまま当てはめる。

- 後回しにした理由: 設計文書がまだ少なく、Pull Request のレビューで防げる
- 見直すきっかけ: 設計文書の要件IDの誤りが、レビューのあとで見つかったとき

---

### 要件から設計文書へのリンク

サイトの要件のページから、その要件に答える設計文書へたどれるようにする。設計文書の「要件」に書いたIDを cumin-trace が読み、逆向きのリンクを作る。設計文書の側には何も足さない。

- 後回しにした理由: v0.1 では、設計文書から要件へのリンクで足りる
- 見直すきっかけ: 要件のページを読んでいて、その設計を探す手間が目立ってきたとき

---

### 生成したファイルの更新

`init` で書いたファイル (skill、テンプレート、図のスクリプト、check の workflow) を、新しいバージョンの cumin-trace に合わせて更新する。`init` は上書きしないので、今は、ファイルを手で書き換えるか、消してから新しいバージョンの `init` を実行する。check の workflow のバージョンも、同じように手で上げる。skill を Claude Code の plugin で配る形にすれば、skill とテンプレートは plugin の更新で済むので、配り方と一緒に決める。

- 後回しにした理由: v0.1 を使うリポジトリは少なく、手で直せる。workflow のバージョンを上げれば、古いテンプレートから書いた文書が新しい書式に合わないとき、書式検査が知らせる
- 見直すきっかけ: skill の配り方を決めるとき。または、cumin-trace の更新を、使っているリポジトリに手で反映する手間が目立ってきたとき

---

### カテゴリを足すコマンド

`cumin-trace add <area>` で、`.cumin-trace.toml` の `areas` にカテゴリを足し、カテゴリのページと図の例を書く。接頭辞は設定から読む。skill は、新しいカテゴリを書くとき、Agent にこのコマンドを実行させる。設定ファイルのコメントと並びを保ったまま書き換える方法は、着手するときに決める。

- 後回しにした理由: v0.1 では、skill の指示に沿って Agent が設定とページを書く。設定に足し忘れても、書式検査が知らせる
- 見直すきっかけ: 2つ目のカテゴリを足すときに、手順の多さが目立ったとき

---

## v0.3 の候補

要件ごとに英語の訳を生成し、生成物として英語のサイトに表示する。元の本文が変わった訳には、古いことを表示する。

- 後回しにした理由: 英語の読み手が、まだいない

複数のプロダクトの集計を、1ページに並べる。

- 後回しにした理由: 公開のプロダクトと private のプロダクトが混ざるので、アクセス制限が必要になる

### cumin-works を使わないリポジトリ

cumin-works を使わないリポジトリでも使えることを確かめ、保つ。要求Issueにラベルを付けないリポジトリでの見分け方も、このときに決める。

- 後回しにした理由: 今の使い手は、cumin-works と組み合わせて使う。対象を広げると、保守する範囲も広がる
- 見直すきっかけ: cumin-works を使わないリポジトリで使いたい人が現れたとき

---

### 導入の手引き

- 後回しにした理由: 自分の使い方が、まだ固まっていない
- 見直すきっかけ: ほかの人に提供すると決めたとき

### private なサイトの公開先

## バージョンを決めていない項目

### 操作できるダッシュボード

Go の `html/template`、htmx、Tailwind を使い、サーバを持つダッシュボードを作る。要求Issueの作成やラベルの変更を、画面から行えるようにする。

- 後回しにした理由: サーバを持つと、置き場所、token、アクセス制限の運用が増える。「GitHub には書き込まない」という原則も変わる
- 見直すきっかけ: ダッシュボードを見たあとに GitHub の画面で行う操作が、毎回同じになってきたとき

---

### SysML v2 への出力

`requirements.json` を、SysML v2 の要求モデルとして出力する。

- 後回しにした理由: 設計や検証までモデルにする必要が、まだない。仕様書も確認していない
- 見直すきっかけ: 設計の要素を、要件と結び付けて管理したくなったとき

---

### 変更の影響範囲

要件を変えたときに、対応する要求Issue、実装Issue、テストを一覧で示す。

- 後回しにした理由: 要件の変更後の起票漏れの検出と、テストとの対応づけが先である
- 見直すきっかけ: その2つができたとき

---

### Jira などへの対応

要求Issueを、GitHub Issues 以外から読む。

- 後回しにした理由: cumin-works も GitHub だけを対象にしている
- 見直すきっかけ: cumin-works が、Issue の管理先を広げたとき
