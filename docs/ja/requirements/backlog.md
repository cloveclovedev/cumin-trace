# backlog

v0.1 には入れないと決めたが、あとで要件に取り入れたいことを書き留める。使い方は cumin-works の backlog と同じである。着手すると決めた項目は、要件のページに書いて、ここから消す。

項目ごとに、内容、後回しにした理由、見直すきっかけを書く。

## v0.2 の候補

### 既存の文書にIDを付ける

cumin-works の `issue-states.md` の遷移や「上位要件のテスト」、peppercheck-next の要件にIDを付ける。短いルールが多く並ぶ文書のために、表の形で要件を書けるようにするかを、このときに決める。遷移の名前 (「request the split」など) をIDの別名として扱うかも決める。

- 後回しにした理由: v0.1 では、新しく書く finance-v2 で書式を確かめる
- 見直すきっかけ: finance-v2 の要件を、1つの領域ぶん書き終えたとき

---

### 要求Issueが古くなったことの検出

要求Issueを書いたあとに要件の本文が変わったものを、見直しの候補として示す。要求Issueにコミットの SHA を書いておき、その SHA の時点と main とで、要件の本文を比べる。

- 後回しにした理由: 要件の変更が、まだ少ない
- 見直すきっかけ: 要件を直したのに、開いている要求Issueを直し忘れたとき

---

### テストとの対応づけ (verify)

テストの名前やコメントに書いたIDを読み、検証が `test` の要件に、対応するテストがあるかを示す。

- 後回しにした理由: v0.1 では、要件から要求Issueまでの区間を先につなぐ
- 見直すきっかけ: 完了した要件の中に、テストのないものが見つかったとき

---

### 要求Issueの下書き

IDを選ぶと、cumin-works の `requirement-issue.md` の形に、要件の本文を並べた下書きを出力する。英語にするのは Agent が受け持つ。

- 後回しにした理由: 並べるだけなら、skill の指示で足りるかもしれない
- 見直すきっかけ: 要求Issueを書く手間のうち、要件の書き写しが目立ってきたとき

---

### 用語の検査

用語集にある語の表記のゆれ (例: レフェリーと審判) を報告する。

- 後回しにした理由: ゆれの候補を、用語集にどう書くかが決まっていない
- 見直すきっかけ: Agent と書いた文書で、表記のゆれを直す手間が目立ってきたとき

---

### 番号の使い回しの検出

git の履歴にあるIDが、別のタイトルで使われていたら報告する。

- 後回しにした理由: レビューで防げる
- 見直すきっかけ: 使い回しが実際に起きたとき

---

### backlog と未決事項の取り込み

backlog の項目と、各ページの「未決事項」を cumin-trace が読み、ダッシュボードに「決めること」として表示する。

- 後回しにした理由: 書式を増やす前に、要件だけで使ってみる
- 見直すきっかけ: 決めることの一覧を、ページをまたいで見たくなったとき

---

### 先のバージョンの要件を前もって書く

要件に「まだ起票しない」ことを表すフィールドを足し、未起票の一覧から外す。

- 後回しにした理由: 今は、作ると決めたことだけを要件文書に書き、後回しは backlog に書く
- 見直すきっかけ: 先のバージョンの要件を詳しく書きためるようになり、未起票の一覧が見にくくなったとき

---

### 受け入れ待ちの表示

進行中のうち、Maintainer の受け入れを待っているものを分けて表示する。

- 後回しにした理由: `cumin/status/*` のラベルを読む必要があり、cumin-works を使わないリポジトリでの扱いを決める必要がある
- 見直すきっかけ: 進行中の要件が増えて、自分の対応を待っているものを見分けにくくなったとき

---

## v0.3 の候補

### 英語版の生成

要件ごとに英語の訳を生成し、生成物として英語のサイトに表示する。元の本文が変わった訳には、古いことを表示する。

- 後回しにした理由: 英語の読み手が、まだいない
- 見直すきっかけ: 製品リポジトリを公開して、英語の読み手に要件を見せたくなったとき

---

### 製品をまたぐ入口

複数の製品の集計を、1ページに並べる。

- 後回しにした理由: 公開の製品と private の製品が混ざるので、アクセス制限が必要になる
- 見直すきっかけ: 3つ以上の製品を載せて、行き来が手間になったとき

---

### 導入の手引き

ほかの人のリポジトリに導入する手順、設定の一覧、書式の説明。

- 後回しにした理由: 自分の使い方が、まだ固まっていない
- 見直すきっかけ: ほかの人に提供すると決めたとき

---

### private なサイトの公開先

Cloudflare Pages と Cloudflare Access を使い、アクセスを制限して公開する手順。

- 後回しにした理由: v0.1 では、手元のプレビューで足りる
- 見直すきっかけ: 手元のマシン以外からダッシュボードを見たくなったとき

---

## バージョンを決めていない項目

### 操作できるダッシュボード

Go の `html/template`、htmx、Tailwind を使い、サーバを持つダッシュボードを作る。要求Issueの作成やラベルの変更を、画面から行えるようにする。

- 後回しにした理由: サーバを持つと、置き場所、token、アクセス制限の運用が増える。「GitHub には書き込まない」という原則も変わる
- 見直すきっかけ: ダッシュボードを見たあとに GitHub の画面で行う操作が、毎回同じになってきたとき

---

### SysML v2 への出力

`requirements.json` を、SysML v2 の要求モデルとして出力する。

- 後回しにした理由: 設計や検証までモデルにする必要が、まだない。仕様書も確認していない
- 見直すきっかけ: 設計の要素を、要件と結び付けて管理したくなったとき

---

### 変更の影響範囲

要件を変えたときに、対応する要求Issue、実装Issue、テストを一覧で示す。

- 後回しにした理由: 要求Issueが古くなったことの検出と、テストとの対応づけが先である
- 見直すきっかけ: その2つができたとき

---

### Jira などへの対応

要求Issueを、GitHub Issues 以外から読む。

- 後回しにした理由: cumin-works も GitHub だけを対象にしている
- 見直すきっかけ: cumin-works が、Issue の管理先を広げたとき

---
