# 要求のbacklog

v0.1 には入れないと決めたが、あとで要件に反映したいことを書き留める。使い方は cumin-works の backlog と同じである。着手すると決めた項目は、要件文書に書いて、ここから消す。

## v0.2 の候補

| 項目 | 内容 | 後回しにした理由 | 見直すきっかけ |
|---|---|---|---|
| 既存の文書へのIDの付与 | cumin-works の `issue-states.md` の遷移と「上位要件のテスト」、peppercheck-next の要件に、IDを付ける。遷移の名前 (「request the split」など) をIDの別名として扱うかを決める | v0.1 は、新しく書く finance-v2 で書式を確かめる | v0.1 の書式で、finance-v2 の要件を1つの領域ぶん書き終えたとき |
| 古さの検出 | 要求Issueを書いたあとで、扱う要件の文面が変わったものを、見直しの候補として出す。要求IssueにコミットのSHAを書いておき、そのSHAとmainで要件の文面を比べる | 文面の変更が、まだ少ない | 要件を直したのに、開いた要求Issueを直し忘れたとき |
| テストとの対応 (verify) | テストの名前かコメントに書いたIDを読み、`検証` が `test` の要件に、テストがあるかを示す | v0.1 は、要求Issueへの1本を先につなぐ | 完了の要件に、テストのないものが見つかったとき |
| 要求Issueの下書き | IDを選ぶと、cumin-works の `requirement-issue.md` の型に、要件の文面を並べた下書きを出す。英語にするのは、Agentの仕事である | 型に並べるだけなら、skill の指示で足りるかもしれない | 要求Issueを書く手間のうち、要件の書き写しが目立ったとき |
| 用語の検査 | 用語集にある語の、表記の揺れ (例: レフェリー と 審判) を報告する | 揺れの一覧を、用語集にどう書くかが決まっていない | Agentと書いた文書で、表記の揺れを直す手間が目立ったとき |
| 番号の使い回しの検出 | gitの履歴にあるIDが、別の題で使われていたら報告する | レビューで足りる | 使い回しが、実際に起きたとき |
| backlog と未決事項を同じモデルに載せる | backlog の表の行と、文書の「未決事項」を、対象が未定の要件や、決める前の項目として読む。ダッシュボードに「決めること」を出す | 書式を増やす前に、要件だけで使ってみる | 決めることの一覧を、文書をまたいで見たくなったとき |

## v0.3 の候補

| 項目 | 内容 | 後回しにした理由 | 見直すきっかけ |
|---|---|---|---|
| 英語の生成 | 要件ごとに英語の訳を生成し、生成物として英語のサイトに出す。元の文面が変わった訳は、古いと表示する | 英語の読み手が、まだいない | 製品リポジトリを公開し、英語の読み手に要件を見せたくなったとき |
| 製品をまたぐ入口 | 複数の製品の集計を、1ページに並べる | 公開とprivateの製品が混ざり、アクセス制限が要る | 3つ以上の製品を載せて、行き来が手間になったとき |
| 導入の手引き | ほかの人のリポジトリに入れる手順、設定の一覧、書式の説明 | 自分の使い方が、まだ固まっていない | 人に渡すと決めたとき |
| privateなサイトの置き場所 | Cloudflare Pages と Cloudflare Access で、アクセスを制限して置く手順 | v0.1 は、手元のプレビューで足りる | Hostや手元のマシン以外から、ダッシュボードを見たくなったとき |

## 版を決めていない項目

| 項目 | 内容 | 後回しにした理由 | 見直すきっかけ |
|---|---|---|---|
| 操作のできるダッシュボード | Go の `html/template`、htmx、Tailwind で、サーバを持つダッシュボードを作る。要求Issueの作成や、ラベルの付け替えを、画面から行う | サーバを持つと、置き場所、token、アクセス制限の運用が増える。「GitHubには書かない」という決まりも変わる | ダッシュボードを見たあとに、GitHubの画面で行う操作が、毎回同じになったとき |
| SysML v2 への書き出し | `requirements.json` を、SysML v2 の要求モデルとして書き出す | 設計や検証をモデルにする必要が、まだない。仕様書も確かめていない | 設計要素を、要件と結んで管理したくなったとき |
| 変更の影響の範囲 | 要件を変えたときに、扱う要求Issue、実装Issue、テストを一覧にする | 古さの検出と、テストとの対応が先である | その2つができたとき |
| Jira などへの対応 | 要求Issueを、GitHub Issues 以外から読む | cumin-works も、GitHubだけである | cumin-works が、Issueの管理を広げたとき |
