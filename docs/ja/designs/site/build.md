# ビルド

[サイトの設計](index.md) の細部。Starlight のビルドが、文書と図から1つのページを作るまでを決める。入力は `docs_dir` の下の文書と図、`.cumin-trace.toml`、`site/` のテンプレートだけである (`CTR-SITE-009`)。cumin-trace のコマンド、出力 (`CTR-EXP-001`)、対応づけの結果 (`CTR-TRC-008`) は読まない。

## 文書を読むローダー

`site/src/content.config.mjs`:

- `docs` のコレクションの `loader` は、`glob({ base: <リポジトリの最上位>/<docs_dir>, pattern: "**/*.md" })` を包むローダーで、`schema` は `docsSchema()` である。
- 包むローダーは、`glob()` の `load()` に、`parseData` だけを差し替えた文脈を渡す。差し替えた `parseData` は、`data.title` がなければ、`filePath` の文書の最初の見出しの文字を `title` にしてから、元の `parseData` を呼ぶ (`CTR-SITE-002`)。
- 最初の見出しは、frontmatter とコードブロックの外にある、最初の ATX 見出し (`#` で始まる行) である。文字は、見出しの記号と前後の空白を除き、コードスパンのバッククォートを除いたものである。見出しがない文書は、ファイル名 (拡張子なし) を `title` にする。
- Starlight は `title` をページの `<h1>` に表示する。最初の見出しを `title` にした文書では、Sätteri のプラグインがその見出しを本文から消す。タイトルが2回出ない。frontmatter に `title` がある文書の見出しは消さない。
- `astro.config.mjs` は、`markdown.processedDirs` に `docs_dir` を渡し、Starlight の Markdown の処理 (見出しのリンクなど) を、`src/content/docs/` の外の文書にもかける。
- ページの URL は、`glob()` の既定の ID (`docs_dir` からの相対パスで、拡張子なし) で決まる。`index.md` は、そのディレクトリの URL になる (推測)。

## 要件の見出しとアンカー

`site/src/requirements.mjs` は、`docs_dir` の下のすべての文書に動く。要件の見出しの決まりは、書式検査と同じである ([文書の読み方](../check/reading.md))。

- `requirements_dir` の下の文書で、文書の最上位にある見出しのうち、最初の子がコードスパンで、その中身が `<接頭辞>-` で始まるものを、要件の見出しとする。中身は、CommonMark のとおり両端の空白を1つずつ除いたものである (hast の `code` の要素の文字)。
- 要件の見出しの中身が正しい形式の ID のときだけ、見出しの `id` を ID そのもの (`CTR-SITE-003`) にする。形式の正しくない要件の見出し (``### `CTR-FMT-01` foo``) は、アンカーを持たないが、要件の見出しとして枠を作り、中の参照をリンクにしない。プラグインが付けた `id` は、Astro が自動で付ける `id` より優先される。
- 見出しの中の ID のコードスパンに、クラス `requirement-id` を付ける。タイトルと見分けが付く形 (枠付きの小さな文字) で表示する (`CTR-SITE-006`)。

## 要件の枠

要件の範囲を `<section class="requirement">` で囲む (`CTR-SITE-006`)。範囲は書式検査と同じで、要件の見出しから、同じレベルか上のレベルの次の見出しの前までである ([文書の読み方](../check/reading.md))。区切り線は範囲に影響しない。

- 子の要件 (下のレベルの要件の見出し) の枠は、親の枠の中に入れ子にする。`### CTR-TRC-004` の次に `#### CTR-TRC-004.1` があれば、子の枠は親の枠の中にあり、次の `###` の前で両方が閉じる。
- 枠の最後のブロックが区切り線のときは、その区切り線を消す。枠の線が区切りの代わりになる。枠の途中の区切り線と、枠の外の区切り線は残す。

`requirements.css` は、枠に、Starlight の変数による1本の線、角の丸み、内側の余白を付ける。続く2つの要件の間には、余白を置く。

## ID の参照のリンク

最初に、`requirements_dir` の下のすべての文書を1回読み、ID からページの URL への表を作る。表は、ビルドの間に1回だけ作る。

参照を読む場所と決まりは、書式検査と同じである ([文書の読み方](../check/reading.md) の「参照」)。

| 場所 | リンクにするか |
|---|---|
| テキストとコードスパン (段落、表、箇条書き、引用、強調、要件ではない見出し、`検証` の行) | する |
| 要件の見出し、`状態` の項目 | しない |
| コードブロック、HTML | しない |
| すでにリンクの中にある文字 | しない。リンクの中にリンクは置けない |

1つのノードの読み方:

1. テキストとコードスパンのノードの値 (表示される文字) で、書式検査の4つの決まりで参照を探す。値の始まりと終わりは、英数字でも `-` でもない文字として扱う。
2. 表にある ID は、`<base><ページ>#<ID>` へのリンクにする。同じページの ID も、同じ形にする。表にない ID は、リンクにしない。

検査との違い: 書式検査は元の文字 (エスケープの前) で読むので、バックスラッシュでエスケープした ID (`CTR-FMT-202\.1`、`CTR\-FMT-200`) と、ノードの境目にまたがる ID は、検査とリンクで結果が違うことがある。このリポジトリの要件文書は、ID をエスケープして書かない。

## 文書のリンク

文書の中のリンクを、宛先によって次のように書き換える (`CTR-SITE-010`)。相対リンクの宛先は、リンクを書いた文書のディレクトリから解決する。

「サイトのページ」は、`docs_dir` の下にあり、実在する `.md` のファイルである。「読める `.puml`」は、`docs_dir` の下にあり、実在する `.puml` のファイルである。

| 宛先 | サイトでの形 |
|---|---|
| 相対パスの `.md` (`#見出し` 付きを含む) で、宛先がサイトのページ | そのページの URL へのリンク。例: `docs_dir` が `docs/ja` で、`designs/site/build.md` の中の `../check/index.md#節` は、`<base>designs/check/#節` になる。見出しの部分は、そのまま残す |
| 相対パスの `.puml` で、宛先が読める `.puml` | ビルドのときにそのファイルを読み、閉じた `<details>` の中のコードブロック (言語 `plantuml`) で中身を表示する。`<details>` は、リンクを含む最上位のブロック (文書の直下の段落、表、箇条書き、見出しなど) のすぐあとに置く。1つのブロックに複数あれば、リンクの順に並べる。`<summary>` は、リンクの文字である。リンクは外す |
| 相対パスの画像 (`![...](...)`) | 下の「図」のとおり |
| ほかの相対パス (サイトのページでない `.md`、読める `.puml` でない `.puml`、サイトに表示しないファイル) | リンクを外し、文字だけを残す。`docs_dir` の外 (`../../README.md` など) と、実在しないファイルを含む。書式検査はリンクの宛先を確かめないためである |
| 外部の URL、`#見出し` だけのリンク | そのまま |

- Starlight は `.md` のリンクを書き換えない (推測)。書き換えないと、文書の間のリンクが切れる。
- `.puml` の中身は、ローダーではなくプラグインが読む。
- `#見出し` の部分は確かめない。宛先のページにその見出しがなければ、リンクは切れる。`check-site` がその切れたリンクを報告する。
- Sätteri のプラグインが作った `<details>` と `<summary>` の HTML のノードが、そのままページに出ること (推測)。Starlight のコードブロック (Expressive Code) が言語 `plantuml` を受け付けること (推測)。受け付けないときは、言語なしのコードブロックにする。

## 図

- 画像のパスが、URL でも `/` で始まるパスでもなく、`./` でも `../` でも始まらないとき、`./` を足す。Astro は、文書からの相対パスで画像を解決する (`CTR-SITE-004`)。`./` のないパスを Astro が解決するかは、公式文書に書かれていないので、`./` を足す。
- 拡大は、`astro.config.mjs` が Starlight の `head` に足す、1行のインラインの `<script>` で作る。本文 (`.sl-markdown-content`) の `<img>` がクリックされたら、`location.href` をその画像の `currentSrc` にする。SVG のファイルだけが、元の大きさで開く (`CTR-SITE-007`)。戻るボタンで文書に戻る。
- リンクで包まずにスクリプトにするのは、Astro が出力に置いた画像の URL を、Markdown のプラグインの段階では知らないためである (推測)。`currentSrc` は、ブラウザが実際に読んだ URL なので、`base` にも画像の置き場所にも左右されない。
- 図として表示するのは、コミットした SVG だけである。`.puml` は描画せず、元の文として折りたたみに表示する (上の「文書のリンク」)。
