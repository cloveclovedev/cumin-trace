# ビルド

[サイトの設計](index.md) の細部。Starlight のビルドが、文書と図から1つの文書のページを作るまでを決める。文書のページの入力は `docs_dir` の下の文書と図、`.cumin-trace.toml`、`site/` のテンプレートだけである (`CTR-SITE-009`)。文書のページは、cumin-trace のコマンド、出力 (`CTR-EXP-001`)、対応づけの結果 (`CTR-TRC-008`) を読まない。対応づけの結果を読むのは、ダッシュボードのページだけである ([ダッシュボードの設計](../dashboard/index.md))。

## 文書を読むローダー

`site/src/content.config.mjs`:

- `docs` のコレクションの `loader` は、`glob({ base: <リポジトリの最上位>/<docs_dir>/ の file URL, pattern: "**/*.md" })` を包むローダーで、`schema` は `docsSchema()` である。`base` は、Astro の文書 ([Content Loader API reference](https://docs.astro.build/en/reference/content-loader-reference/) の `glob()` の `base`) のとおり、相対パスか URL で渡す。`pathToFileURL()` の URL は、パスの `#` と `?` もパスとして保つ。最後の `/` は、ディレクトリとして解決させるためである。
- 包むローダーは、`glob()` の `load()` に、`parseData` だけを差し替えた文脈を渡す。差し替えた `parseData` は、`data.title` がなければ、`filePath` の文書の最初の見出しの文字を `title` にしてから、元の `parseData` を呼ぶ (`CTR-SITE-002`)。
- frontmatter は、Astro のローダーと同じ決まりで見つける。`requirements.mjs` の `frontmatter()` と `body()` は、Astro 7.4.0 の `parseFrontmatter()` (`@astrojs/internal-helpers`) の正規表現の写しを持つ。BOM、`---` のあとの空白、`\r\n` の行末、前の空行を、Astro と同じに扱う。本文 (`body()`) は、Astro と同じく、frontmatter を空白にして前後を `trim()` した文字である。Astro の内部のパッケージには依存しない。写しが Astro とずれると、見出しの行がずれ、`check-site` の `testdata/site-cases/` (下の「確かめ方」) が失敗する。
- 最初の見出しは、本文のコードブロックの外にある、最初の ATX 見出し (`#` で始まる行) である。文字は、見出しの記号と前後の空白を除き、コードスパンのバッククォートを除いたものである。見出しがない文書は、ファイル名 (拡張子なし) を `title` にする。この決まりは `requirements.mjs` の `firstHeading()` だけが持ち、ローダーとプラグインが同じものを使う。
- Starlight は `title` をページの `<h1>` に表示する。最初の見出しを `title` にした文書では、Sätteri のプラグインがその見出しを本文から消す。タイトルが2回出ない。frontmatter に `title` がある文書の見出しは消さない。消すのは、プラグインの `after` (すべての訪問のあと) で、文書の最上位にある見出しのうち、`firstHeading()` の見出しと同じ行で始まるものである。行は、本文の中の行番号で、プラグインは `options: { position: true }` でノードの位置を読む。setext 見出しや HTML の見出しが前にあっても、それは消さない。プラグインは、Sätteri のプラグインの factory で、パーサーが読む本文 (`source`) と、Astro が解析した frontmatter のデータ (`data.astro.frontmatter`) を受け取る。このデータは、ローダーの `parseData` が受け取るデータと同じで、`title` の有無を同じに決める。`check-site` だけは、YAML を解析せずに、frontmatter の行の始めに `title:` (引用符付きを含む) があるかで決める (`hasTitle()`)。最初の見出しが要件の見出し (下の「要件の見出しとアンカー」) のときは、消さない。その要件のアンカーと枠を残すためで、ページではタイトルと要件の見出しの両方が出る。
- `astro.config.mjs` は、`markdown.processedDirs` に `docs_dir` を渡し、Starlight の Markdown の処理 (見出しのリンクなど) を、`src/content/docs/` の外の文書にもかける。
- ページの URL は、`glob()` の ID で決まる。ローダーは、`glob()` の `generateId` に `requirements.mjs` の `pageID()` を渡す ([Content Loader API reference](https://docs.astro.build/en/reference/content-loader-reference/) の `generateId`)。`pageURL()` も `pageID()` から URL を作るので、両方が同じ決まりに従う。
- `pageID()` は、`docs_dir` からの相対パスから `.md` を除き、各部分を小文字にし、文字、数字、`_`、`-` でない文字の並びを1つの `-` にする。空白、`#`、`?` は `-` になり、`_` は残る。`index.md` は、そのディレクトリの ID になる。frontmatter の `slug` は使わない。

## 要件の見出しとアンカー

`site/src/requirements.mjs` は、`docs_dir` の下のすべての文書に動く。要件の見出しの決まりは、書式検査と同じである ([文書の読み方](../check/reading.md))。

- `requirements_dir` の下の文書で、文書の最上位にある見出しのうち、最初の子がコードスパンで、その中身が `<接頭辞>-` で始まるものを、要件の見出しとする。中身は、CommonMark のとおり両端の空白を1つずつ除いたものである (hast の `code` の要素の文字)。
- 要件の見出しの中身が正しい形式の ID のときだけ、見出しの `id` を ID そのもの (`CTR-SITE-003`) にする。形式の正しくない要件の見出し (``### `CTR-FMT-01` foo``) は、アンカーを持たないが、要件の見出しとして枠を作り、中の参照をリンクにしない。プラグインが付けた `id` は、Astro が自動で付ける `id` より優先される。
- 見出しの中の ID のコードスパンに、クラス `requirement-id` を付ける。タイトルと見分けが付く形 (枠付きの小さな文字) で表示する (`CTR-SITE-006`)。

## 要件の枠

要件の範囲を `<section class="requirement">` で囲む (`CTR-SITE-006`)。プラグインの `after` が、文書の最上位の子を並べ直した新しい root で、元の root を置き換える。範囲は書式検査と同じで、要件の見出しから、同じレベルか上のレベルの次の見出しの前までである ([文書の読み方](../check/reading.md))。区切り線は範囲に影響しない。

- 子の要件 (下のレベルの要件の見出し) の枠は、親の枠の中に入れ子にする。`### CTR-TRC-004` の次に `#### CTR-TRC-004.1` があれば、子の枠は親の枠の中にあり、次の `###` の前で両方が閉じる。
- 枠の最後のブロック (空白だけのテキストを除く) が区切り線のときは、その区切り線を消す。枠の線が区切りの代わりになる。枠の途中の区切り線と、枠の外の区切り線は残す。

`requirements.css` は、枠に、Starlight の変数による1本の線、角の丸み、内側の余白を付ける。続く2つの要件の間には、余白を置く。

## 検証の枠

要件の `検証` の行を、本文と分けて、要件の枠の中の小さな枠に入れる (`CTR-SITE-016`)。`blocks()` が枠を作ったあとに、`boxVerifications()` が動く。

- 各 `section.requirement` (入れ子の枠も) の直下の番号のない箇条書き (`ul`) から、文字が `検証:` で始まる項目を取り出す。`検証` の行の決まりは、書式検査と同じである ([文書の読み方](../check/reading.md))。
- 取り出した項目を、元の箇条書きのすぐあとに置く `<div class="requirement-verification">` に入れる。中身は、`検証` の文字 (`span.requirement-verification-label`) を1つと、各項目から先頭の `検証:` を除いた箇条書き (`ul`) である。元の箇条書きにほかの項目が残らなければ、枠が元の箇条書きの場所に入る。
- `検証` の文字を枠に1回だけ置き、行ごとの `検証:` を除くのは、行が2つ以上ある要件で同じ文字が繰り返されないためである。元のファイルは変えない (`CTR-SITE-002`)。

本文の最後の箇条書きと `検証` の行の間に空行があると、CommonMark では両方が1つの箇条書きになり、`検証` の行が本文の項目に見える。ビルドで分けるので、文書の書き方は変えなくてよい。

`requirements.css` は、小さな枠に、要件の枠と同じ色の1本の線、小さい角の丸み、小さい文字 (`--sl-text-sm`)、小さい内側の余白を付ける。`検証` の文字は、小さな枠の左上の線に重ね、ページの背景の色 (`--sl-color-bg`) を敷いて線を隠す。行は、枠の中の左端から始め、印を付けない。行が2つ以上なら、行の間に小さな余白を置く。場所をできるだけ取らないためである。

- 採らなかった案: 文書の書式を変え、`検証` の行を1つの項目の下の入れ子の箇条書きにする。書式、書式検査、テンプレート、すべての文書を変えることになる。表示だけで同じ見た目になる。

## ID の参照のリンク

最初に、`requirements_dir` の下のすべての文書を1回読み、ID からページの URL への表を作る。表は、ビルドの間に1回だけ作る。

参照を読む場所と決まりは、書式検査と同じである ([文書の読み方](../check/reading.md) の「参照」)。

| 場所 | リンクにするか |
|---|---|
| テキストとコードスパン (段落、表、箇条書き、引用、強調、要件ではない見出し、`検証` の行) | する |
| 要件の見出し、`状態` の項目 | しない |
| コードブロック、HTML | しない |
| すでにリンクの中にある文字 | しない。リンクの中にリンクは置けない |

1つのノードの読み方:

1. テキストとコードスパンのノードの値 (表示される文字) で、書式検査の4つの決まりで参照を探す。値の始まりと終わりは、英数字でも `-` でもない文字として扱う。
2. 表にある ID は、`<base><ページ>#<ID>` へのリンクにする。同じページの ID も、同じ形にする。表にない ID は、リンクにしない。

検査との違い: 書式検査は元の文字 (エスケープの前) で読むので、バックスラッシュでエスケープした ID (`CTR-FMT-202\.1`、`CTR\-FMT-200`) と、ノードの境目にまたがる ID は、検査とリンクで結果が違うことがある。このリポジトリの要件文書は、ID をエスケープして書かない。

## 文書のリンク

文書の中のリンクを、宛先によって次のように書き換える (`CTR-SITE-010`)。相対リンクの宛先は、リンクを書いた文書のディレクトリから解決する。

「サイトのページ」は、`docs_dir` の下にあり、実在する `.md` のファイルである。ただし、`.` で始まるディレクトリの下の文書と、`.` で始まる名前の文書は、ページがないので除く (下の「サイドバー」)。「読める `.puml`」は、`docs_dir` の下にあり、実在する `.puml` のファイルである。

| 宛先 | サイトでの形 |
|---|---|
| 相対パスの `.md` (`#見出し` 付きを含む) で、宛先がサイトのページ | そのページの URL へのリンク。例: `docs_dir` が `docs/ja` で、`designs/site/build.md` の中の `../check/index.md#節` は、`<base>designs/check/#節` になる。見出しの部分は、そのまま残す |
| 相対パスの `.puml` で、宛先が読める `.puml` | ビルドのときにそのファイルを読み、閉じた `<details>` の中のコードブロック (言語 `plantuml`) で中身を表示する。`<details>` は、リンクを含む最上位のブロック (文書の直下の段落、表、箇条書き、見出しなど) のすぐあとに置く。1つのブロックに複数あれば、リンクの順に並べる。`<summary>` は、リンクの文字である。リンクは外す |
| 相対パスの画像 (`![...](...)`) | 下の「図」のとおり |
| ほかの相対パス (サイトのページでない `.md`、読める `.puml` でない `.puml`、サイトに表示しないファイル) | リンクを外し、文字だけを残す。`docs_dir` の外 (`../../README.md` など) と、実在しないファイルを含む。書式検査はリンクの宛先を確かめないためである |
| 外部の URL、`#見出し` だけのリンク | そのまま |

- Starlight は `.md` のリンクを書き換えない (推測)。書き換えないと、文書の間のリンクが切れる。
- 書き換えるのは、`requirements.mjs` の `linksPlugin` である。`astro.config.mjs` は、`hastPlugins` に `linksPlugin`、`requirementsPlugin` の順に渡す。`requirementsPlugin` の `after` は木全体を置き換えるので、同じプラグインの中でリンクも書き換えると、その置き換えが効かなかった (`check-site` で確かめた)。別のプラグインにすると、リンクの書き換えが終わった木を `requirementsPlugin` が読む。
- 宛先の種類は、`linkTarget()` が決める。URL の形 (`https:` などの scheme で始まる)、`/` で始まるパス、`#` で始まるリンクは、そのままにする。パスの部分は、パーセントエンコードを `decodeURIComponent()` で戻してから解決する。`%23` (`#`) と `%3F` (`?`) も戻る。`?` 以降は捨てる。
- `.puml` の中身は、ローダーではなくプラグインが読む。1つの最上位のブロックの最初の `.puml` のリンクを読むときに、そのブロックのすべての `.puml` のリンクの `<details>` を、リンクの順に、ブロックのすぐあとに置く。
- リンクを外すときは、リンクの文字 (`textContent`) だけを残す。リンクの中のコードスパンの見た目は残らない。
- `#見出し` の部分は確かめない。宛先のページにその見出しがなければ、リンクは切れる。`check-site` がその切れたリンクを報告する。
- Sätteri のプラグインが作った `<details>` と `<summary>` は、そのままページに出る。Starlight のコードブロック (Expressive Code) は、言語 `plantuml` のコードブロックを、エラーなしで `plaintext` として表示する。このリポジトリの文書で、`check-site` で確かめた。

## 図

- 画像のパスは、元の文書のまま変えない。Astro は、URL でも `/` で始まるパスでもない画像のパスを、文書からの相対パスとして解決し、ファイルを出力の `_astro/` に置く (`CTR-SITE-004`)。`./` のないパス (`site-build.svg`) も同じである。`@astrojs/markdown-satteri` 0.4.4 のコードで確かめ、`check-site` が毎回確かめる。
- プラグインは画像の `src` を変えない。Astro は画像のパスを mdast の段階で集め、hast の `src` がその文字と同じ `<img>` だけを画像として扱うためである。
- 拡大は、`astro.config.mjs` が Starlight の `head` に足す、1行のインラインの `<script>` で作る。スクリプトの文は、`requirements.mjs` の `diagramScript` で、`check-site` も同じ文を読む。本文 (`.sl-markdown-content`) の `<img>` がクリックされたら、`location.href` をその画像の `currentSrc` にする。SVG のファイルだけが、元の大きさで開く (`CTR-SITE-007`)。戻るボタンで文書に戻る。
- リンクで包まずにスクリプトにするのは、Astro が出力に置いた画像の URL を、Markdown のプラグインの段階では知らないためである (推測)。`currentSrc` は、ブラウザが実際に読んだ URL なので、`base` にも画像の置き場所にも左右されない。
- 図として表示するのは、コミットした SVG だけである。`.puml` は描画せず、元の文として折りたたみに表示する (上の「文書のリンク」)。

## サイドバー

`requirements.mjs` の `sidebar(settings, root)` が、Starlight の `sidebar` の項目の配列を返す。`astro.config.mjs` が、ビルドとプレビューの始めに1回呼ぶ (`CTR-SITE-011`、`CTR-SITE-015`)。

- 読むリンク: 文書の本文の、画像でないインラインのリンク (`[文字](宛先)`) を、書いた順に読む。frontmatter、コードブロック、コードスパン、HTML のコメントの中は読まない。読み方は、`requirements.mjs` の `sourceLinks()` と、それが使う `bodyLines()` が決め、`sidebar()` と `check-site` が同じ関数を使う。使うのは、`linkTarget()` が「サイトのページ」とする宛先だけである。`#見出し` の部分は捨てる。
- 項目: ページは `{ slug: <pageID()> }` で、表示は Starlight がそのページの `title` にする。ディレクトリ `D` の `index.md` は、グループ `{ label, items }` になる。`label` はその文書のタイトル (frontmatter の `title`、なければ最初の見出し) で、`requirements.mjs` の `documentTitle()` が決める。`check-site` も同じ関数を使う。`items` の最初は、その `index.md` のページである。
- リンクの文字: リンクが置いたページは `{ slug, label }` になり、`label` はリンクの文字である。リンクが置いたグループの `label` も、リンクの文字である。文字の `` ` `` は除き、前後の空白を除く。文字が空のときは、上の「項目」のとおりタイトルになる。「残り」で置くページとグループは、リンクがないので、タイトルかディレクトリの名前になる。Starlight 0.42.6 の `slug` の項目は、`label` を書けば、その文字を表示する (`dist/schemas/sidebar.js` の `InternalSidebarLinkItemSchema` で、`label` は省ける文字である。2026-10-30 にパッケージのコードで確かめた)。
- 見出しのグループ: `docs_dir` の `index.md` の `##` の ATX 見出しは、それぞれ最上位のグループ `{ label, items }` になる。`label` は見出しの文字で、`` ` `` を除く。見出しの下から次の `##` 見出しまでのリンクが、そのグループの中に並ぶ。最初の `##` 見出しより前のリンクは、最上位に並ぶ。`###` より深い見出しは、グループを作らない。見出しを読むのは `docs_dir` の `index.md` だけで、ほかの `index.md` の見出しは、グループを作らない。項目が1つもない見出しのグループは、出さない。見出しの読み方は `requirements.mjs` の `sections()` が決める。
- 順: `docs_dir` の `index.md` のリンクを、書いた順に置く。`docs_dir` の `index.md` のページは、サイドバーに置かない。サイトの左上の名前が、`docs_dir` の `index.md` のページへのリンクである (Starlight 0.42.6 の `dist/components/SiteTitle.astro` が、`dist/utils/routing/data.js` の `getSiteTitleHref()` の `formatPath("/")` へリンクする。2026-10-30 にパッケージのコードとビルドした HTML で確かめた)。`docs_dir` の `index.md` が自分へリンクしても、そのリンクは飛ばす。グループの中は、その `index.md` のリンクの順に、`D` の下のページを置く。`D` の外へのリンクは、グループの中では飛ばす。
- 1回だけ: 各ページは、サイドバーに1回だけ出る。最初に置いた場所に出し、あとのリンクは飛ばす。各 `index.md` は、まず自分のリンクをすべて置き、そのあとで、置いたグループを順に、そのグループの `index.md` のリンクで埋める。そのため、`docs_dir` の `index.md` が `D/index.md` と `D/x.md` の両方にリンクすれば、`D/x.md` は `docs_dir` の `index.md` の場所に出る。たどるのは `index.md` のリンクだけである。ほかの文書のリンクは、順に影響しない。
- 残り: 「残り」は、たどり終えたあとに、どこにも置かれていないページのすべてである。どこからもリンクしていないページだけでなく、`index.md` でない文書だけがリンクするページと、ほかのグループの `index.md` だけがリンクするページも含む。残りは、たどり終えてから1回で決め、次のとおりに置く。
  - 残りのページは、そのページを持つ最も深いグループの最後に置く。どのグループにも入らないページは、最上位の最後 (見出しのグループのあと) に置く。グループは、たどる間に作った、`index.md` のあるディレクトリのグループである。見出しのグループは、ディレクトリを持たないので、残りを受けない。
  - 残りの中は、`docs_dir` からの相対パスの順 (文字コードの順) である。
  - 残りの中で、まだグループのないディレクトリは、グループになる。`index.md` があれば上の決まりでその文書のタイトルを `label` にし、なければディレクトリの名前を `label` にする。その中も、パスの順である。
- 1つだけのグループ: 残りを置いたあとで、ディレクトリのグループのうち、項目がその `index.md` のページ1つだけのものは、そのページの項目 `{ slug, label }` になる。`label` はグループの `label` である。カテゴリのディレクトリが `index.md` と図だけを持つとき、サイドバーには同じ名前の行が1つだけ出る。
- `docs_dir` の `index.md` がないときは、すべてのページが「残り」になる。
- ページ: `sidebar()` が置くのは、`docs` のコレクションが読む文書だけである。`.` で始まるディレクトリの下の文書と、`.` で始まる名前の文書は、`glob()` が読まないので、ページがない。`requirements.mjs` の `dotPath()` がこれを決め、`check-site` も、これらの文書のページを求めない。ページのない `slug` がサイドバーにあると、`astro build` は止まる。
- `docs_dir` の `index.md` のページの ID は `index` である (`pageID()`)。Starlight がこの `slug` でトップのページを指すことは推測で、`check-site` で確かめる。

## 言語

`astro.config.mjs` は、Starlight に `locales: { root: { label: "日本語", lang: "ja" } }` を渡し、`defaultLocale` を書かない (`CTR-SITE-012`)。

- UI (検索、目次、ページ送りなど) の文字は、Starlight の日本語の訳になる。`<html>` の `lang` は `ja` になる。`check-site` が、各ページの `lang` と、検索のボタン、目次、ページ送りの文字を確かめる。検索の索引 (Pagefind) の UI も同じ言語になる (推測)。
- ページの ID は `pageID()` のままで、`docs_dir` の中のパスから始まる。`root` の言語は、ID にも URL にも言語のディレクトリを足さない。
- サイドバーは `sidebar()` の項目だけを出す。Starlight の既定のサイドバー (ファイルの構成から作るもの) は使わない。

## 確かめ方

`check-site` は、このリポジトリの文書のほかに、`testdata/site-cases/` の文書でも確かめる。`testdata/site-cases/check.sh` は、`site/` を一時ディレクトリに写し、その文書で `check-site` を動かす。`npm --prefix site ci` のあとに動かす。

| 文書 | 確かめること |
|---|---|
| `requirements/Data Model_v2.md` | 大文字、空白、`_` のパスの要件への参照が、そのページとアンカーに行く (`CTR-SITE-003`) |
| `trace.json` (`docs/` の外) | `check.sh` が `site/trace.json` に写す。ダッシュボードの木とカテゴリの名前が、決まりから手で書いた値と同じになり、要件と Issue のリンクが行き先に合う (`CTR-DASH-001`、`CTR-DASH-005`)。読んだ時刻が、ビルドの手元の時間帯と関係なく、手で書いた日本時間 (`2026-10-17 18:10:55`、`2026-1-5 5:05:03`) になる (`CTR-DASH-006`)。そのあと JSON でない `trace.json` を書き、ページが GitHub を読めなかった1文だけを表示することを確かめる (`CTR-DASH-006`) |
| `headings/` | 受け付けるどの見出しの形でも、タイトルが1回だけ出て、本文に繰り返さない。本文がタイトルと同じ文字の見出しを ATX、setext、HTML のどれで繰り返しても、その見出しは残る (`CTR-SITE-002`) |
| `frontmatter/` | frontmatter に `title` がある文書は、書き方が違っても、最初の見出しを本文に残す (`CTR-SITE-002`) |
| `server/`、`functions/` | `server` や `functions` という名前の文書のディレクトリのページは、サーバの関数ではない (`CTR-SITE-008`)。`check.sh` は、そのあと `functions/` の文書を消し、`site/public/functions/` にファイルを置いて、`check-site` が失敗することも確かめる |
| `links/` | `#`、`?`、空白を名前に持つファイルへのリンクが、そのページに行く (`CTR-SITE-010`) |
| `sidebar/` | `docs_dir` の `index.md` のリンクの順にサイドバーが並び、置いたページとグループがリンクの文字を表示する。`docs_dir` の `index.md` の `##` 見出しが最上位のグループになり、`docs_dir` の `index.md` は、自分へリンクしても、サイドバーに出ない。`docs_dir` の `index.md` が `gamma/index.md` と `gamma/one.md` の両方にリンクすると、`gamma/one.md` は `docs_dir` の `index.md` の場所に出て、`index.md` だけになった `gamma` のグループは、そのページの項目1つになる。`index.md` でない文書だけがリンクするページ、ほかのグループの `index.md` だけがリンクするページ、どこからもリンクしていないページが、それぞれ「残り」の決まりの場所に1回だけ出る。`check.sh` は、`sidebar()` の最初の項目を、決まりから書いた項目と比べる。`.drafts/draft.md` と `.hidden.md` があり、`docs_dir` の `index.md` が `.drafts/draft.md` にリンクしても、ビルドが通り、サイドバーに出ないことも確かめる (`CTR-SITE-011`、`CTR-SITE-015`) |

`?` を名前に持つファイルは、Go のモジュールに入れられないので、`check.sh` が書く。

`check-site` は、タイトルと同じ文字の見出しの数を、ページと文書で同じ決まりで数える。ページでは本文の `<h1>` から `<h6>` を、文書では ATX 見出し、setext 見出し、HTML の見出し (`<h1>` から `<h6>`) を数える。文書の setext 見出しは、`=` か `-` の行で終わる段落である。リストの項目、引用、表の行に続く `-` の行は、setext 見出しとしない。`check-site` は、見出しの文字を、空白と `*`、`_`、`` ` ``、`~`、`\` を除き、リンクを文字だけにして比べる。HTML のコメント、HTML のブロック、リストの中の `#` の行も、ATX 見出しとして読む。そのような行が最初の見出しより前にあると、タイトルはその行の文字になり、本文の見出しが残る (知られた制限)。タイトルになった見出しの中の相対リンクは、見出しとともに消えるので、`check-site` はそれを切れたリンクとして報告する (知られた制限)。
